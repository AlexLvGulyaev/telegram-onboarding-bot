## Findings

### F1. Базовая версия успешно сохраняет результат в PostgreSQL

После завершения диалога в таблице `training_results` появилась корректная запись со всеми обязательными полями.

### F2. Вопросы теста дублируются

В прогоне с целевой моделью `gpt-5.4-mini-2026-03-17` вопросы 1 и 4 были про одно и то же: «как команда общается по умолчанию» / «как команда использует коммуникацию по умолчанию».

Причина: системный промпт не требует от модели следить за уникальностью вопросов; `TrainingService` не отслеживает уже заданные вопросы.

**Влияние:** снижается качество оценки знаний; тест формально из 5 вопросов, но фактически охватывает меньше материала.

### F3. Последний вопрос может быть не задан явно

В конце прогона с целевой моделью пользователь написал «Следующий вопрос?», а бот воспринял это как ответ и завершил тест, не задав 5-й вопрос явно.

Причина: модель сама управляет фазами и не получает жёстких инструкций о том, что вопрос должен быть явно сформулирован до оценки ответа.

**Влияние:** тест может завершиться досрочно или некорректно.

### F4. Дублирование точки входа

В репозитории две точки входа:
- `main.py` (корень) — делегирует запуск;
- `bot/main.py` — основная логика запуска.

Это не критично, но затрудняет понимание структуры.
## Выводы

Baseline-версия бота технически работает: контейнеры поднимаются, бот отвечает в Telegram, результат сохраняется в PostgreSQL. Однако качество диалогового процесса требует доработки:

1. **Усилить системный промпт**, чтобы модель однозначно переходила к тестированию по сигналу пользователя.
2. **Добавить контроль уникальности вопросов** — не допускать повторов в рамках одной сессии.
3. **Ужесточить логику перехода к completed**: тест завершается только после явного задания и ответа на `total_questions` вопросов.
4. **Привести структуру точки входа к одному файлу**.

Эти улучшения войдут в доработанную версию бота.

### Findings

#### F5 (подтверждён). Двойной запрос готовности перед тестом

**Наблюдение:** на теме «Кибербезопасность» бот дважды выдал обучающий блок и спросил «Готовы?» перед первым вопросом.

**Корневая причина:** модель не всегда следует системному prompt и вместо перехода к `phase=testing` возвращает ещё один обучающий ответ с мета-вопросом «Готовы к тесту?». Этот мета-вопрос извлекается из `reply` как `current_question`, что создаёт лишний ход.

**Устранение:**

1. Усилен системный prompt `prompts/v1/system.md`: при сигнале готовности модель должна сразу переключать `phase=testing` и задавать первый вопрос по материалу, без мета-вопросов и без повторения обучения.
2. Дополнительно усилен inline-prompt в `_build_prompt()` в `services/ai_training_service.py`.
3. В `TrainingService.apply_ai_turn()` добавлен guard: если переход в `testing` произошёл по ключевому слову пользователя, а модель не вернула явный `next_question`, любой вопрос, извлечённый из `reply`, игнорируется, и guard fallback запрашивает реальный первый вопрос.

#### F7 (устранён). Имя сотрудника с ключевыми словами сразу переводило в тест

**Наблюдение:** при имени `Тест Кибербезопасности` обучающая фаза пропускалась.

**Корневая причина:** после регистрации имени в `process_ai_training()` в качестве `user_message` для первого обучающего хода передавалось само имя сотрудника. Поскольку в имени есть слово «Тест», `wants_to_start_test()` срабатывало и мгновенно переводило сессию в `testing`.

**Устранение:** первый обучающий ход теперь запускается с нейтральным сообщением `Пожалуйста, начни объяснение материала.`, которое не содержит ключевых слов. Имя по-прежнему сохраняется в `draft.employee_name`.

### Итоги по F5 и F7

Оба дефекта устранены комбинацией усиления системного prompt и небольшого guard в логике применения AI-хода. Это не «костыль», а явное правило протокола диалога: при явном сигнале пользователя о готовности бот обязан перейти к первому вопросу, а не задавать уточняющий мета-вопрос.

## Финальный раунд: D1, F9, F10, F11, чистое разделение промпта

**Дата:** 2026-08-11 (часть 4)
**Статус:** ✅ Все целевые дефекты устранены. Прогон после рефакторинга промпта — чистый.

### D1. Дублирование вопросов в UI

**Симптом:** в фазе testing бот показывал пользователю дубль предыдущего вопроса, хотя модель в `next_question` уже вернула новый. На теме `cybersecurity-staff` давало 4/5 вместо 5/5.

**Корень:** `bot/handlers/onboarding.py::_format_bot_reply()` показывал `ai_turn.reply`, а канонический вопрос хранится в `draft.current_question` (из `ai_turn.next_question`). Старый guard `if "?" in reply: return reply` пропускал дубль, если в reply был любой вопрос.

**Устранение:** `_format_bot_reply()` переписана — в фазе testing из `reply` оставляются только не-вопросительные предложения (feedback), и всегда добавляется канонический `draft.current_question`. FSM и scoring не трогались (они работали корректно).

### F9. Бот не спрашивал готовность после обучения

**Симптом:** бот сразу после обучения задавал первый вопрос, без явного запроса готовности.

**Устранение:** в `prompts/v1/system.md` добавлено поведенческое правило — в конце обучения явно спросить готовность и остаться в фазе learning.

### F10. Лишний 6-й вопрос перед завершением

**Симптом:** после 5-го ответа бот задавал 6-й вопрос и тут же выдавал 5/5.

**Корень:** при `phase=completed` и `current_question=None` условие `draft.phase != "testing" or not draft.current_question` в `_format_bot_reply` было истинно, и функция возвращала `reply` с лишним вопросом.

**Устранение:** финальное сообщение вынесено в `_send_final_result()`; после `apply_ai_turn` при `updated_draft.phase == "completed"` сразу отправляется финал, `ai_turn.reply` не показывается. `final_summary` берётся из `draft.final_summary` с fallback на `last_ai_turn.reply`.

### Пропадающий feedback при guard fallback

**Симптом:** когда модель в `reply` давала только feedback без следующего вопроса, срабатывал guard fallback, и в Telegram приходил только вопрос — feedback пропадал.

**Устранение:** внутри guard fallback сохраняется `updated_draft.last_answer_feedback`, и `fallback_reply` формируется как `{feedback}\n\n{следующий вопрос}`.

### F11. Дубль вопроса по смыслу (разные формулировки)

**Симптом:** вопрос 5 повторил факт вопроса 1 в другой формулировке («Какой минимальной длины должен быть сложный пароль?» vs «Какой должна быть минимальная длина сложного пароля?»). Keyword-dedup не сработал (формулировки разные), embedding-dedup не сработал (`max_similarity=0.198` при threshold 0.82).

**Устранение:**
1. `_DUPLICATE_EMBEDDING_THRESHOLD` понижен с 0.82 до 0.72 (короткие русские вопросы кластеруются ниже типичного диапазона 0.80–0.85).
2. В технический слой (`_build_prompt()` и `request_question()`) добавлена инструкция: `next_question` не должен повторять по смыслу вопросы из `asked_questions`; выбирать факт, ещё не покрытый.

### Чистое разделение промпта

В ходе устранения F9/F10/F11 технические инструкции (правила заполнения JSON-полей, `asked_questions`, `phase=...`) попали в `prompts/v1/system.md` — это свело на нет смысл выноса промпта из хардкода «на пользовательский уровень». Принято решение о чистом разделении:

- **`prompts/v1/system.md`** — роль + тема + материал + поведенческие правила + запреты. Без имён JSON-полей, без `phase=...`, без `asked_questions`.
- **Технический слой** (`_build_prompt()` / `request_question()` в `services/ai_training_service.py`) — сериализованное состояние, правила заполнения JSON-полей, переходы phase, дедуп по `asked_questions`.
- JSON-схема ответа — отдельно в `prompts/v1/response-schema.json`, уходит в API через `response_format`.

См. `docs/PROMPT_ARCHITECTURE.md` и `task_history/2026-08-11_task-prompt-clean-separation.md`.
